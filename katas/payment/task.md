## Задача

Реализуйте в `solution.py` класс `OrderService` с ровно такой сигнатурой
конструктора:

```python
class OrderService:
    def __init__(self, gateway: PaymentGateway) -> None: ...
    def place_order(self, amount: float) -> str: ...
```

`place_order` должен вызвать `gateway.charge(amount)` и вернуть то, что
вернул `charge` — без своей логики поверх.

## Требование, которое легко нарушить

**`OrderService` не должен создавать платёжный шлюз внутри себя** —
ни `StripeGateway()`, ни любой другой конкретный класс, захардкоженный
в `__init__` или `place_order`. Единственный способ получить шлюз —
через параметр конструктора.

Если захардкодить конкретную реализацию внутри `OrderService`, тесты
ниже, которые подставляют тестовый шлюз (fake) и проверяют, что вызван
именно он, — не пройдут: `OrderService` их вызов проигнорирует и
воспользуется своим захардкоженным шлюзом. Это Dependency Inversion
Principle: модуль верхнего уровня (`OrderService`) зависит от
абстракции (`PaymentGateway`), а не от конкретной реализации, и
получает эту абстракцию, а не создаёт её сам.

## Зачем

Тот же приём вы увидите в Students API и Auth-сервисе: сервисный слой
получает репозиторий/клиент через конструктор, а не создаёт его сам —
это то, что позволяет подменить реальную БД на тестовую в контрактных
тестах, не трогая код сервиса.
